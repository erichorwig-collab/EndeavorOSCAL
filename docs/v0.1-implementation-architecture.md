# v0.1 implementation architecture

## Decision

Endeavor v0.1 uses Python 3.11+ with a small standard-library CLI and a
separated OVAL parsing, OSCAL emission, provenance, and test surface. The
current proof-of-concept package is intentionally small so the mapping contract
can be exercised before the external schema toolchain is available.

The current proof-of-concept has these validation dependencies:

- `lxml` for securely configured XML parsing and the vendored compatibility
  XSD bundle. The validated producer profile is OpenSCAP OVAL 5.11.3; the
  5.12.2 bundle is retained for future-release compatibility work.
- project-local AJV for test-gate validation against the released schema's
  ECMA-262 regular expressions and a vendored, hash-pinned Assessment Results
  schema. Python `jsonschema` is useful for structural experiments but cannot
  validate the 1.2.0 release schema on Python 3.14.

`convert` itself emits an atomically written, schema-shaped document but does
not shell out to Node/AJV. The pinned AJV gate is exercised by the test suite;
making per-invocation OSCAL validation a production runtime feature remains a
separate, explicit design decision.

Avoid a broad application framework or unbounded XML convenience layer in
v0.1. `argparse`, `hashlib`, `uuid`, `json`, `pathlib`, and dataclasses are
sufficient for the CLI and normalized model.

## Target package layout

```text
endeavor/
  cli.py             stable inspect and convert commands
  oval/              bounded parse, validation, normalized model
  oscal/             pure normalized-model to OSCAL transformation
  provenance.py      hashes and deterministic UUIDv5 identifiers
  io.py              bounded reads and atomic writes
  schemas/           vendored, hash-pinned OVAL and OSCAL schemas
tests/
  unit/ integration/ security/ golden/
```

The current single-module proof-of-concept will be split into this layout as
the vendored schema boundary is introduced. No public CLI or artifact contract
is promised before that split is covered by tests.

## Required parser and validation boundary

1. Read only a regular local file, with a strict byte limit; hash the exact
   bytes before parsing.
2. Parse with `lxml.etree.XMLParser(resolve_entities=False, load_dtd=False,
   no_network=True, huge_tree=False, recover=False)`.
3. Ignore `xsi:schemaLocation`; resolve XSD imports only beneath Endeavor's
   packaged schema directory.
4. Validate the supported OpenSCAP 5.11.3 producer profile against the
   vendored compatibility schemas; retain 5.12/5.12.2 as a future-release
   compatibility track.
5. Normalize only expected namespace-qualified elements and reject duplicate or
   missing identifiers.
6. Emit canonical UTF-8 JSON, validate it against the pinned OSCAL schema, and
   perform semantic provenance checks before atomically replacing the output.

## Determinism and privacy

- Use UUIDv5 names derived from contract version, schema version, input hashes,
  run metadata, and OVAL definition identifiers. SHA-256 remains the integrity
  value; UUIDs are identifiers only.
- Sort definitions and properties and exclude absolute paths and wall-clock
  time from deterministic values.
- Do not embed raw source XML by default. Emit sanitized relative references
  and SHA-256 values; make raw-evidence inclusion an explicit future option.
- Diagnostics identify artifact role and safe filename only. They never echo
  raw XML, secrets, or absolute host paths.

## Security test gate

The production validation gate covers malicious DTDs/entities, XInclude,
external and local entity references, invalid UTF-8, excessive depth and
width, oversized files, a deterministic malformed-input corpus, malicious
schema locations, path traversal, missing or duplicate definition identifiers,
mismatched source documents, and atomic no-output-on-error behavior. OVAL XML
is bounded at 5 MiB and 50,000 elements; archive/resource limits remain
explicit preconditions for the future ARF/XCCDF ingestion phase. Golden tests
must compare canonical bytes for all six OVAL result states.
