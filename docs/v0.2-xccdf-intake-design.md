# XCCDF intake design - Phase 4 foundation

The first SCAP-expansion increment is inventory-only XCCDF 1.2 Results intake.
It will not create OSCAL findings or infer control mappings. It establishes the
shared secure SCAP parser boundary before ARF collection support.

Supported producer target: OpenSCAP 1.4.4 XCCDF 1.2.1, validated against the
restricted vendored XSD bundle recorded in `endeavor/schemas/MANIFEST.md`.
`inspect-xccdf --results FILE` retains only safe
inventory/provenance: benchmark and TestResult IDs, rule-result IDs/statuses,
selected profile, target facts, evaluator metadata, timestamps, SHA-256, and
safe filename. It must preserve `pass`, `fail`, `error`, `unknown`,
`notchecked`, and `notapplicable` without normalization loss.

The initial command uses the upstream synthetic fixture recorded in
`fixtures/xccdf-results/`; it does not change the representative alpha
validation inputs. DTD/entity, XInclude, unsafe schema hint, and over-limit
tests are covered. Evaluator metadata and tailoring preservation remain before
claiming the normalized XCCDF model complete. A separate sanitized companion
fixture records and tests evaluator, profile, tailoring reference, identity,
target facts, rule timing/weight, and score without altering the upstream
fixture or alpha workflow inputs. ARF follows only after this
model exists:
its first slice is a bounded collection manifest that rejects ambiguous result
components by default and preserves component hashes and tailoring links.

The pinned ARF collection fixture is recorded in `fixtures/arf/` with its
immutable upstream commit and SHA-256. It is a synthetic OpenSCAP 1.4.4 unit
fixture and intentionally does not claim a production assessment or tailoring
coverage.

`inspect-arf --results FILE` now exposes an inventory-only manifest of ARF
assets, requests, reports, relationships, and C14N component hashes. It
resolves component references only within the collection and requires exactly
one local collection and asset linkage for each XCCDF TestResult report. It
does not dereference content or interpret report semantics. Tailored-evidence
normalization remains the next increment.

For a linked XCCDF report, Endeavor retains the embedded TestResult inventory
and resolves its declared benchmark ID to exactly one local checklist component.
The benchmark `href` remains literal provenance and is never fetched. This is
not yet an XCCDF-to-OSCAL mapping or tailoring interpretation. If the
TestResult names a profile, it must resolve exactly once in that linked local
Benchmark; absent profiles remain absent rather than inferred.

ARF-linked XCCDF target names, addresses, facts, target references, evaluator,
and execution identity are preserved literally. The ARF `isAbout` relationship
remains the authoritative report-to-asset linkage; matching target-reference
values are recorded as evidence, not treated as an inferred identity rule.

Embedded ARF OVAL reports retain each evaluated definition ID and exact OVAL
status alongside their canonical report-content hash. The pinned fixture does
not provide a unique local definitions-component match for every such report,
so Endeavor intentionally reports no inferred component linkage.
